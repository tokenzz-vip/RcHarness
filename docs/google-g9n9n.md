# Google Chromecast Voice Remote（G9N9N）适配

在 macOS 蓝牙设置中配对遥控器，再到 RcHarness 的「连接与语音 → 更换遥控器…」选择 Google 蓝牙遥控器。按住返回与主页键进入配对模式。按键映射需要输入监控与辅助功能权限；语音还需要蓝牙权限，并在语音应用中选择 RcHarness 的回环输入设备。

## 识别与按键

设备身份集中在 `Core.swift` 的 `RemoteProfiles.googleG9N9N`：HID VID/PID 为 `18D1:9450`，蓝牙名称包括 `Chromecast Remote`；语音连接通过型号 `G9N9N` 或 BLE PnP ID（相同 VID/PID，厂商来源 1 或 2）校验。真机固件 26.2 的 Device Information 型号是 `A0`，厂商来源是 1；`A0` 本身不作为通过身份验证的依据，仍需精确匹配 PnP 身份。仅共享 ATVV 服务 UUID 不足以通过身份验证。

G9N9N 使用 Consumer Page（`0x0C`），按下为非零值，释放为零：

| 实体按键 | Usage |
| --- | --- |
| OK | `0x41` |
| 上／下／左／右 | `0x42`／`0x43`／`0x44`／`0x45` |
| 返回／主页 | `0x224`／`0x223` |
| 音量 +／−／静音 | `0xE9`／`0xEA`／`0xE2` |
| 电源／输入源 | `0x19E`／`0x89`（兼容旧映射 `0x189`） |
| YouTube／Netflix | `0x77`／`0x78` |
| 语音 | ATVV BLE START／STOP |

按键表已通过 2026-11-07 的 G9N9N 测试设备 固件 26.2 逐键采集核对；输入源实际是 `0x89`，修正了原先依据 [VibeMote 的实机 HID 映射](https://github.com/Tilkmilk/vibe-mote/blob/main/keys.py) 填写的 `0x189`，并保留旧别名。`0x42` 必须按型号解析，不能复用小米的返回键含义。电源、输入源和音量键如果已被电视配置为仅发红外，macOS 无法读取该红外信号，需要在原电视设置中调整；本应用只接收实际发送的蓝牙报告。

共有 15 项逻辑输入，支持普通按键的单击、双击、长按和实物图上的实时按压反馈。新建默认方案的静音／输入源／YouTube／Netflix 分别为静音、切换原生模式、复制、粘贴。已保存方案不被覆盖，新增键缺少配置时保持禁用。切换型号保留方案和 Harness；不受新型号支持的全局按键回退到电源键并保留原动作。

## 语音

复用 ATVV v1、16 kHz IMA ADPCM 和既有回环音频输出。Google 长按沿用已实测的 16 kHz ADPCM 握手参数；点按声明模型级别 3，以保留原生 HTT 按下／释放，再在短按释放后请求 on-request 流；不修改长按参数或现有 16 kHz 编码。两种模式均要求有效的能力回复，不将任意语音服务视为就绪。按协商的有界帧长缓冲和连续解码，不再固定要求小米的 120 字节；AUDIO_SYNC 重置预测器并清理未完成帧。线格式参考 [ATVVoice v1 实现](https://github.com/b0o/ATVVoice/blob/main/src/protocol/v10.rs) 与 [握手定义](https://github.com/b0o/ATVVoice/blob/main/src/protocol/mod.rs)。

Google 的语音键可以没有独立 HID 事件，因此长按模式从 BLE 流开始／结束生成去重的实体按键边沿，再进入同一权限检查、快捷键和尾音排空流程。断连、取消、切换型号会释放状态。默认仍为按住说话，松手停止收音。可在「按键 → 语音键 → 点按模式」手动启用点按，并将快捷键设为目标输入法的点按快捷键；模式变更后重新连接语音服务以协商参数。点按参考 [ATVVoice PR #27](https://github.com/b0o/ATVVoice/pull/27) 的 HTT 手势流程，由 Swift 状态机独立实现：

1. 原生 `AUDIO_START(reason=3)` 记下按下时间与本次按下前是否已在持续录音。保留原生音频，同次 `START_SEARCH` 仅作为重复通知，首次按下只发一次输入法开始快捷键。
2. 收到真实 `AUDIO_STOP(reason=2)` 才判定释放。首次按下不足 550 毫秒时，保留输入法会话与已缓存音频，发送 `MIC_OPEN = 0C 00`；不提前发送 MIC_CLOSE 终止物理按压。
3. 第二次原生按下即标记为结束，释放后排空尾音并配对结束快捷键，不再发送 MIC_OPEN。按住达到 550 毫秒时同样释放结束，不锁存。
4. 没有对应按下记录的额外 `STOP(reason=2)` 不结束正在开启或已开启的主机流。其他 STOP、错误、取消与主动停止仍正常清理。没有原生 START 的 SEARCH 可直接请求，独立 HID 点击在释放后与 BLE 合并。
5. MIC_OPEN 后 1 秒内必须收到可解码的音频帧；START 回复、重复通知和不完整音频不能取消或重置此期限。每 5 秒 MIC_EXTEND 续期；连续 2 秒无音频、单段流 120 秒、断连、休眠、切换模式或退出均有结束保护。主动停止缺少 STOP 时最多等 0.5 秒。

音频输出和虚拟麦克风协议不变。写命令失败会清除就绪状态并自动重连；电量特征发现失败仅显示电量未知，不中断核心连接。

## 点按模式的验证边界

此前先关闭原生流、在物理按键释放前发送 MIC_OPEN 的实现，在本机固件 26.2 上多次得到 START 但音频包为零，切换开麦参数也未恢复音频。该实现已由上述“保留原生流、释放后开麦”流程替换。

协议回归覆盖原生 START／SEARCH 合并、首次释放接管及保留前段音频、第二次原生点击结束、重复释放、首次有效帧超时、部分帧与重复 START、原生与 HID 合并、长按不锁存、取消与拒绝、超时后恢复、尾音、续期及小米隔离。实机结果见下段；模拟回归本身不等同于所有固件或输入法均兼容。

2026-11-11 安装该版后，用户反馈“测试效果可以，暂时满足要求”，本轮保留此版并结束调整。18:19 的元数据确认了一次成功点按：约 209 毫秒松手后发送 MIC_OPEN，主机流持续约 9.48 秒，收到 466 包、解码 149,120 个样本；再次原生点击约 164 毫秒后结束，整段输出 152,000 个样本，丢弃为 0，输入法开始／结束快捷键各配对一次。日志同时仍有零音频触发保护的尝试，因此本次属于当前设备与输入法配置的阶段验收，不视为全部快速点按场景已稳定。其他固件及豆包、讯飞仍需分别验收。记录仅含协议与音频计数，不保存音频或识别文本。

## 验证边界

自动化覆盖全部 Consumer 按键及释放、型号隔离、PnP 身份、协商帧长与分包解码、语音边沿去重、原生按键抑制恢复、切换与保存、实物图点击区域。截图渲染可追加 `--remote-profile google-g9n9n`，仅在隔离的渲染设置中选择型号，不改变用户设置。

2026-11-07 已连接 G9N9N 测试设备（固件 26.2、硬件 PVT/MP、型号字符串 A0），逐一验证 14 个普通按键的按下／释放，均收到蓝牙报告，其中输入源重复按了两次，均成对释放。采集范围为按键 usage、按下／释放及 HID 描述符，不包含设备地址、序列号或音频；原始采集附件不随公开文档发布。

修正后已在应用中复测输入源按下／释放及语音键：PnP 身份确认成功、电量 100%、ATVV v1／16 kHz／160 字节帧协商成功；一次约 4.5 秒的按住说话收到 214 包、解码及输出 68,480 个样本，松手后停止采音并排空输出，快捷键正常释放，丢弃样本为 0。复测仅记录连接、按键和音频计数，不保存音频或识别文本。15 项实体输入均完成本次识别验收；244 项 Swift 单元测试通过。

首次配对、短按语音、快速重复、休眠重连、两种遥控器同时连接，以及退出后原生音量恢复仍需分别验收。仿制遥控器可能使用不同身份或不提供 ATVV 服务，本适配不据外壳型号自动放行。
