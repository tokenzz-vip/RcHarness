## 修复前的问题与证据

### F1 · P1：小米遇到错误型号后停止继续发现

位置：[XiaomiRemoteVoice.swift](../Sources/RcHarness/XiaomiRemoteVoice.swift#L188)，关联 `discover()`（144 行）、`connect()`（252 行）。

`receiveModelNumber()` 发现小米型号不符时取消连接超时，然后直接返回；没有断开候选、清空 `remote`、累计失败或安排下一次发现。`discover()` 又要求 `remote == nil`，所以这个错误候选只要保持连接，就会占住整个连接状态。后续唤醒正确遥控器不会自动触发新扫描；普通按键也因型号确认未通过而保持不可用。

触发例：保存了旧遥控器 UUID，换成另一款小米后重新启动；或共享名称的候选先返回了与当前档案不符的型号。显式切换型号会清除记忆 UUID，因此不能把所有正常的型号切换都宣称为复现。

建议：保留型号不符的诊断，但结束该候选连接，按 peripheral UUID 暂时排除，继续发现并定期复查。不能通过放宽型号校验解决。还应把记忆设备按 profile 保存；目前共用一个键，并在切换时删除，会失去各型号的重连记忆。

验证：源码确认。现有 `XiaomiRC001Tests` 只直接调用型号接收并检查匹配结果，没有驱动真实的连接/超时/重新发现流程；本次未用真机复现此连接状态。

### F2 · P2：移除一个 HID 服务时，普通按键没有释放

位置：[XiaomiRemoteHID.swift](../Sources/RcHarness/XiaomiRemoteHID.swift#L188) 与 `deviceRemoved()`（331 行）。

parser 只记录 Hat Switch 的方向状态，`reset()` 只返回这些方向的释放。普通 Keyboard/Consumer 按键不在 reset 状态里。移除某个服务时，如果还有其他匹配服务，manager 不发送总断连，应用也就不会执行 `gestures.cancel()`。

因此，在多 HID 服务或同型号多设备场景中，先将 OK 映射为按住 Command，再按住并移除承载它的服务，Command 可能保持按下，延迟手势也可能继续触发。单设备完整断开时已有总断连取消逻辑，不应把它描述成所有断连都会卡键。本次看到的小米只有一个 device 记录，未证明其具有多个 HID 设备对象。

建议：在设备层跟踪所有活跃按键，移除该设备时逐一释放；保留来源身份到路由层，并以来源集合聚合相同逻辑按键，避免释放另一只仍按住的遥控器。

验证：隔离测试对四款 parser 均复现：按下 OK 后 reset，手势输出只有 `[down]`，缺少预期的 `[down, up]`。完整设备移除的硬件拓扑仍需实测。

### F3 · P2：两个输入持有同一合成键时，先松开的输入会释放另一方

位置：[SystemEventSender.swift](../Sources/RcHarness/SystemEventSender.swift#L76)、[RemoteGestureController.swift](../Sources/RcHarness/RemoteGestureController.swift#L64)，语音快捷键入口位于 `sendShortcut()`（175 行）。

各手势虽然保存自己的映射，但最终输出没有按键持有权聚合。将 OK 和返回都映射为“按住左侧 Command”，依次按下两键，再松开 OK，就会发出清除 Command 标志的释放事件，而返回仍在按住。普通映射与语音快捷键复用同一修饰键时也存在同类冲突。

建议：为手势、语音和宏分配输出 owner，在统一合成事件边界维护键/鼠标键的持有集合；只有最后一个 owner 释放时才发送 up。组合快捷键还要保留其他活跃修饰键。取消 owner 应释放该 owner 的输出，不能简单清空全局状态。

验证：通过 `postEvent` 注入捕获 CGEvent 复现，未向真实会话投递事件。两键按下后释放第一键，最后事件的 Command 标志已清空。

### F4 · P2：退出时一次瞬时恢复失败，会遗留原生按键抑制

位置：[RemoteVolumeSuppression.swift](../Sources/RcHarness/RemoteVolumeSuppression.swift#L188)、`restore()`（304 行）。

EOF 是退出/崩溃后的恢复信号，但末尾的 `restore()` 一旦抛错，就进入最外层 catch 并结束辅助进程。恢复日志会保留，这是正确的；但是没有当次有界重试。只要某次 `hidutil` 短暂失败，遥控器的原生按键就可能继续被映射到零，直到下一次辅助进程启动恢复，或设备服务重建。

建议：退出时做有界退避重试；成功恢复的 snapshot 及时从日志移除，失败项继续保留。前台应用存活时，辅助进程的异常退出应反馈到应用，避免只在系统日志里记录失败。

验证：用注入的 hidutil 实现模拟“抑制成功，第一次恢复抛出错误，后续调用本可成功”。worker 返回后映射仍为 suppression，恢复日志仍存在。全部在临时目录和内存映射中完成，没有修改系统键映射。

### F5 · P2：多个 BLE 候选时没有自动复查

位置：[XiaomiRemoteVoice.swift](../Sources/RcHarness/XiaomiRemoteVoice.swift#L153)。

`retrieveConnectedPeripherals` 返回多个候选时只更新状态，不扫描、不安排 fallback、不保留这些候选的断连监听。如果用户随后断开多余设备，而 central 的电源状态没有变化，就没有这条路径自身提供的再次发现触发；通常需要手动“立即重新连接”。这与 F1 的错误型号占位是两种不同控制流。

建议：在“多个候选”的状态也安排可取消的定时复查；先恢复“只剩一个候选”后的自动连接。若之后支持候选选择，应让用户选设备 UUID，再验证型号，不能按发现顺序随意接管。

验证：源码确认；没有注入 CBCentralManager 的现成测试接口，本次未进行多只硬件的端到端复现。

## 审计提出的优化（处理结果见文末）

1. **让 BLE 连接流程可测试。** `XiaomiRemoteVoice` 直接创建 central、使用系统 uptime 和 DispatchWorkItem；现有确定性时钟主要覆盖手势及语音会话控制器。抽出很小的连接状态机，注入发现/连接接口与现有 Scheduler，优先覆盖 F1、F5、型号读失败、通知失效、超时后更换候选和旧连接回调。按仓库约定使用 TestClock。
2. **共用 usage 规则，减少解析与抑制漂移。** 当前 parser 还接收 Keyboard Esc/Backspace、Consumer Play/Pause、Voice Command 等别名，suppression 列表却没有这些 source。若某固件确实发这些别名，就可能同时执行原生和映射动作。它们是否出现在目标硬件上尚待抓包，所以这是兼容性风险，不能说当前四款均存在双重触发。建议每个 adapter 定义一份 usage→逻辑输入表，解析和抑制共同使用，并明确标注仅诊断用途的别名。
3. **明确区分型号与具体设备。** 当前 `modelNumber` 是整个 HID manager 的一个值，不能将 BLE UUID 绑定到具体 HID 设备；RC001/RC003 的同 VID/PID 限制由此产生。先取得可用的设备地址/序列等实机证据，再决定如何关联；证据不足时在界面主动提示只连接一只小米。
4. **保留实验性适配状态到界面。** 文档说明 GY3LE 实验性，但 `RemoteProfileMenuItems` 与型号卡片没有展示支持成熟度。可在 RemoteProfile 增加“已实测/待实测/实验性”元数据，并在选择菜单和连接页显示。RC001、G9N9N 也应准确说明尚待本项目实机验收的范围。
5. **增强可用的诊断导出。** 当前 `copyDiagnostics()` 只有权限和就绪布尔值。补充选中型号、检测型号、连接阶段、协商帧长、输出 UID、最近失败原因和版本，排查“等待连接”会更直接。不要导出音频或识别文本。
6. **让显式刷新真正重新枚举音频设备。** `refreshDevices()` 读 `AudioDeviceCatalog` 的缓存，正常情况下依赖 HAL listener 失效缓存。若 listener 注册失败或遗漏通知，点击“刷新音频设备”仍得到旧缓存。为显式刷新提供 invalidate/reload 入口；常规状态刷新继续使用缓存。
7. **用单调时间统计单次语音时长。** 连接与门控已使用 uptime，dashboard 时长却用 Date 差值；录音中调整系统时间会导致统计丢失或异常放大。日期仍用于按天归档，持续时间改用可注入单调时钟。
8. **清理适配命名和文档遗留。** 共享传输仍命名为 Xiaomi，Google 的诊断也显示 Xiaomi；可在下一次相关重构中改名为 ATVV/Remote，避免另起无收益的大改。`docs/behavior.md` 的每日语音排行上限仍写 13，代码已按全部型号最大输入数计算为 15。

## 已验证的基础能力

- 设备身份集中于 RemoteProfile，Google 使用独立 Consumer 映射，未把小米的 `0x42` 含义混用。
- 小米型号校验和 Google 型号/PnP 校验与 ATVV 能力协商分开，型号确认本身不会直接标记语音就绪。
- 配置按遥控器隔离，切换、恢复、全局键归一化、旧配置迁移有专门测试；本次未发现应优先于 F1–F5 的配置隔离问题。
- 语音会话已经处理 HID/BLE 乱序、重复边沿、连续会话排队、取消后的释放、启动缓存和尾音排空，现有压力测试通过。
- 原生按键抑制采用独立进程、精确服务匹配和恢复日志；日志先于抑制落盘，并保留其他工具修改的映射。这些设计应保留。
- 音频输出有串行配置、过期回调隔离、缓存上限、两次重建预算和启动超时；HAL 包含 epoch flush、多个读取者与 producer loss 检查。
